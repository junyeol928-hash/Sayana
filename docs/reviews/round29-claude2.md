## 4. SOTD に届かない理由(効き目の大きい順)

Execute Program・Brilliant・Josh W. Comeau のコースと並べると、本文を読む間の現在地と、PC で書いて藍に染まる瞬間は、この道場の方が上になった。負けるのは 3 つ。**どの入口から戻っても、狙った所の頭に着く**こと(相手はハッシュでも外さない)。**結果を読み上げでも受け取れる**こと。**試して壊したときの例外を、正しい行と読める長さで返す**こと。審査員は PC のホームで「演習へ進む」を押し、3 本に 1 本は「演習」の見出しが見えない画面に着く。1 を直せば Usability の U2 と L5 の「一部」が消え(Usability 8.5・L 9.0、加重平均 8.65)、2 まで直せば Usability 9.0 も見える。3 の塗りを直せば Design の D2 の「一部」が消える。

### 1. 段の頭へのハッシュで開くと、軸ができる瞬間に読む所が流される(ホームの「演習へ進む」)
- 軸・項目: Usability U2、学びやすさ L5
- 画面: 撮り足し home-main-to-write(spring-di、#write が 102px。狙いは 230px)。全レッスンを `#write` で開くと 1440px で 17 / 54 の見出しが隠れ(java-strings −46px・java-datetime −22px・spring-reading-code −24px・capstone-requirements −2px ほか)、230px に着くのは 0。1280px は 10 / 54 が隠れる。1279px は 54 / 54 が 230px
- 問題: ブラウザはハッシュの段へ 230px で着く(50ms)。その直後、`await loadCodeMirror()` のあとで `buildRail` が `.has-rail` を付け(`.lesson-main` の `position: relative`・`padding-left`・帯の `display: none`)、同じ瞬間に編集欄が CodeMirror に替わって、上の段の高さが数百 px 変わる。ブラウザの位置合わせは、祖先の位置や余白が変わると働かない決まりがあり(見込み)、直しきれない。「読み直す」「続きから」「用語集」は今回 `afterSettle` で着地をやり直すようになったが、段の頭へのハッシュは `spotQuiz` の正規表現(`#quiz-qN` だけ)にも入らない。ホームの主ボタンは、前回の段が済んでいれば「〇〇へ進む」= ハッシュの形なので、翌朝の最初の 1 押しがここを通る
- 直し方:
  - `spotQuiz` を「ハッシュの着地」全般にする: `location.hash` が段の id(`#read`・`#atwork`・`#run`・`#quiz`・`#write`・`#reading`・`#sts`・`#terms`・`#columns`・`#more`)なら、`trackLesson()` の直後に `el.scrollIntoView({ block: "start" })` を 1 回、さらに `afterSettle` でもう 1 回(読む人が動いていなければ)
  - 根から断つなら、軸の有無で上の段の高さが変わらないようにする: 1280px 以上の 1 列では、帯の `.stepper-wrap` を最初から `visibility: hidden; height: 0` にする CSS を `.no-tutor` だけで当て(JS が動かないときは `<noscript>` か `:not(.js)` で戻す)、`.lesson-main` の `padding-left` も `.has-rail` を待たずに付ける
  - `review-shots.mjs`: 全レッスンを `#write` で開いた 3 秒後の見出しの位置(1440・1280px。目標は 230±12 が 54 / 54)と、ホームの「〇〇へ進む」で開いた撮影を足す

### 2. 演習の採点結果と「読んだ」の結果が読み上げられない
- 軸・項目: Usability U4(学びやすさ L3 の、読み上げで使う人にとっての手応え)
- 画面: 演習の採点(java-hello をキーボードで提出。フォーカスは「提出して採点」に残り、次の Tab は「雛形に戻す」)、撮り足し dye-ai-after の「藍に染まった(演習もできた)」
- 問題: `lesson.html` の `.grade-slot` には読み上げの領域が無く、採点のあとのフォーカスも動かさない。サンプルの結果とクイズの結果は aria-live、手を止めてと復習は判定へフォーカスを移すので、演習だけが黙る。PC の主役の手を動かす場面で、合格・不合格も、藍に染まった 1 行も、読み上げでは届かない。「読んだ」はボタンごと `outerHTML` で差し替わり、フォーカスが消えて「読了。次は下のサンプルを動かしてみよう」も読まれない
- 直し方:
  - `app.js` の `htmx:afterSwap` で `.grade-result` を受けたら、`.grade-banner` に `tabindex="-1"` を付けて `focus({ preventScroll: true })`(復習の判定と同じ形)。判定の 1 行は「合格(5 / 5 テスト合格)」と読めるように `✔` を `aria-hidden` に。藍に染まった 1 行は判定の直後なので、続けて読まれる
  - 「読んだ」は差し替え後の `.read-done` に `tabindex="-1"` を付けてフォーカスを移すか、`.read-action` を `aria-live="polite"` にする
  - AI が未設定なら「ヒント」も出さない(講評・翻訳のボタンと同じ扱い)。出すなら押せない形を枠の破線などで押せるボタンと分ける

### 3. サンプルの実行時例外が、朱の塗りの箱で、理由が右に切れ、場所を「1行目付近」と言う
- 軸・項目: Design D2、学びやすさ L3(細かい所。答えではなく試した結果)
- 画面: 撮り足し npe-1280・npe-1440(java-if の「input を null にしてみる」をそのとおりにした結果)、run-exception・run-exception-dark(java-variables で 2 行目の `s.length()`)。比べに ex-exception(演習の実行時例外は「Warikan.java:6」と正しい行)
- 問題: `JShellRunner.describe` は JShell のスタックトレースの行番号をそのまま出す。JShell は文ごとに別のスニペットにするので、トップレベルの文はどこで落ちても「1行目付近」になる(コンパイルエラーは `lineOf(offset)` で編集欄の行に直している)。理由の文は `REPL.$JShell$12.input` と中の名前を含み、`.exception` が `white-space: pre` なので、肝心の「… is null」が 1280px で 244px 右に切れる。箱は `--ng-soft` の塗りで、暗い表示では錆色の塊。サンプルのコメントが例外を起こして見るよう誘うのは 149 本中 10 本で、学ぶ人が予想どおりに壊したときに、場所を間違えて教える
- 直し方:
  - `JShellRunner`: スニペットを評価するときに、その文の始まりの行(`lineOf(offset)` と同じ数え方)を覚え、`EvalException` の各行のうち `REPL.$JShell$N` のものに足して「7 行目」と出す。分からないときは行を出さない
  - 理由の文の `"REPL\.\$JShell\$\d+[A-Z]?\.` を `"` に置き換える(`simplify` と同じ規則。「because "input" is null」になる)
  - `app.css` の `.exception` を、スマホの例外と同じく塗らない形に: `background: var(--code-bg); color: var(--code-ink); white-space: pre-wrap; overflow-wrap: anywhere;`(左の朱の線は外側の `.run-result` がすでに持つ)。1 行目の例外名だけ朱の文字に
  - 撮影に「サンプルの実行時例外」(明るい・暗い表示)を足す
